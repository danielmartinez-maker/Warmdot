# P0.4 Audio, Scene Transitions, and Game UI Design

**Status:** Implementation design for the authorized P0 engine milestone. The product proposal and `docs/roadmap/forge2d-implementation-plan.md` remain the scope authority.

## Goals

- Give games a Forge-owned audio API for short effects, streamed music, and named mix buses.
- Let gameplay request a transition by stable scene GUID and make replacement atomic.
- Add a retained game UI tree with panel/image/text/button elements, layout, pointer interaction, keyboard focus, and runtime rendering.
- Keep editor chrome on egui and keep audio/UI rendering out of the fixed-step world simulation.

## Audio boundary

A `forge_audio` crate owns the public playback handles and command types. Kira is an implementation detail pinned behind that API. The initial desktop adapter uses Kira 0.12.5, with static playback for short effects and streaming playback for music. Built-in buses are `master`, `music`, `sfx`, and `ui`; bus changes must validate finite volume values and fail with a Forge error.

Project audio assets are discovered only below `Assets/`, use stable catalog GUIDs, and are opened through the asset catalog's canonical-path checks. The initial admitted formats are WAV and OGG. Decoding and playback errors become diagnostics; they do not unwind the simulation or terminate the editor.

Luau exposes `Forge.Audio.play(assetGuid, bus?)` and `Forge.Audio.play_music(assetGuid, loop?)`, which append bounded commands to the current callback context. Commands are committed only when the callback completes successfully, then drained by the host outside deterministic simulation. No arbitrary path or native Kira handle is exposed to scripts.

## Scene transition boundary

Luau exposes `Forge.Scene.load(sceneGuid)`. It queues a bounded transition request; it never reads files itself. The player maps the requested stable GUID to a project-owned scene beneath `Scenes/`, parses and validates the document and its asset dependencies, and prepares the replacement runtime before swapping. A missing, invalid, or dependency-broken target leaves the active runtime intact and reports a structured diagnostic.

A successful swap uses the existing scene replacement reset contract for scripts, physics, input, time, and debugger state. The player then rebuilds scene-bound UI and continues rendering. Only one transition request is accepted per fixed tick; requests are ordered by script callback order and the first valid request wins.

## Game UI boundary

A new `forge_ui` crate owns versioned `.forgeui.json` documents, retained element identity, layout, focus, input routing, and draw extraction. Scene documents reference an optional UI document GUID. The initial widget set is panel, image, text, and button, with bounded tree depth/count, explicit anchors and min/preferred sizes, deterministic child order, and simple vertical/horizontal layout.

The UI tree is independent of ECS entities and editor egui state. Pointer and keyboard input is routed to the focused UI tree before gameplay actions, with an explicit consumed/unconsumed result. Button activation emits a bounded UI event into the Forge event path. Image widgets reference catalogued PNG GUIDs. Text uses an engine-provided bitmap font for the first slice so projects render offline without external font files.

The renderer draws world sprites first and game UI second in a screen-space pass. UI extraction reports asset GUID and sprite data through Forge-owned types; the renderer does not take dependencies on Taffy or document schemas.

## Failure and compatibility rules

- Unknown audio, scene, UI, and image GUIDs produce actionable diagnostics.
- Audio/UI command queues and widget trees have explicit caps.
- Existing schema version 1 scenes remain readable when the optional UI reference is absent.
- New UI documents are independently versioned; migration fixtures and round-trip coverage are scheduled under P0.5.
- The Kira version and formats are pinned and documented; no cross-platform latency or deterministic audio claim is made.
- No external asset download or script execution is introduced by this milestone.

## Implementation order

1. Add bounded audio asset discovery/loading and the Forge-owned Kira adapter.
2. Add transactional script audio commands and player playback, then use an authored sample HUD/menu.
3. Add queued scene transition requests, project scene indexing, validation, and safe runtime replacement.
4. Add the retained UI document/tree, layout, focus/input, rendering pass, and action-sample HUD/menu interaction.
5. Update the P0 roadmap and Windows CI evidence after each integrated slice.
